# FieldSync M5 security review

Reviewed on 2026-11-17 against local real PostgreSQL, Redis/BullMQ, MinIO and browser checks, with the evidence transport updated to R2-compatible PUT on 2026-11-18. This is a review of implemented controls and deployment requirements; live R2/cloud infrastructure and a paid AI provider have not been exercised.

| Boundary | Implemented control and verification |
| --- | --- |
| Tenant/actor identity | Session-derived organization and actor; explicit tenant predicates and composite FKs for users, inspections, evidence, revisions, jobs, AI artifacts and reviews. Analytics also restrict workers to current assignments. Cross-tenant and same-tenant cross-inspection references are rejected in actual PostgreSQL tests. No RLS policies are claimed. |
| Sessions and writes | Argon2id passwords; random session tokens stored as SHA-256 digests; HttpOnly/SameSite=Lax cookies, Secure in production. Exact Origin and JSON guards apply to every API mutation including login. Unknown keys, body limits, version checks and stable mutation receipts prevent injected ownership/provenance and stale writes. |
| AI review | Jobs persist immutable original suggestions and model/source provenance separately. Only an assigned worker with explicit confirmation can atomically apply edited fields to a current editable version. Admins can reject suggestions and approve submitted reports through the existing human workflow. Stale/closed/reassigned sources cannot overwrite reports. Lost review responses retry identical bodies. |
| Provider boundary | Server/worker-only key; fixed official API host, structured-output validation and bounded responses/timeouts. Image requests send only selected verified bytes; report/voice requests send relevant frozen checklist context. No credentials, organization ID or worker email are sent by the adapter. Untrusted text/images are data, and provider output is rendered as text. Missing keys, refusals or failures return labeled fallbacks without fabricated observations/transcripts. |
| Abuse controls | Auth burst limit 60/minute per peer; AI burst 10/minute per tenant/user. In-process maps are bounded and expire. PostgreSQL serializes a 20/hour per-actor AI budget across API instances. Burst limits are per process, not a distributed brute-force guarantee. Untrusted forwarded headers cannot bypass the default direct-host guard; hosted proxy trust must match ingress. |
| Private evidence | Tenant-prefixed staging/verified keys; constrained short-lived SigV4 PUT signatures; actual size/MIME signature/SHA-256 verification; server-only immutable promotion; authorized downloads and sandboxed escaped HTML archives. Removal and rollback cleanup validate key ownership. Submitted/approved/cancelled membership is read-only. |
| Browser/offline | Isolated organization/user Dexie databases; transactional Blob/metadata/outbox saves; quota failures preserve input for retry. Web Locks coordinate editors/replay. Service worker caches only production shell/static assets, never API/auth/storage responses. Logout isolates retained work; site-data deletion or device loss can still lose unsynced content. |
| HTTP and logging | Helmet CSP with same-origin scripts and configured storage connect origin; blob media, microphone permission for self, camera/geolocation disabled. No-store private responses, request IDs, no raw error details, secret redaction and no routine body/provider-output logging. API listener has bounded header/request times and shutdown. |
| Hosting and recovery | HTTPS application/storage required in production; URL adapters support verified external PostgreSQL/Redis TLS. Private Render database TLS limitations and network allowlists are documented. Paid backups, dedicated bucket, minimal service identities, restore validation and deployment/account gate are in the deployment/recovery guides. |

The real tests cover authorization, confirmation, request/AI-review/output rollback, immutable provenance, stale sources, quota failure, lost responses, actual worker retry/fencing and restored receipts/artifacts/objects. Browser checks cover the manual workflow with AI disabled, offline MediaRecorder attachments, review/approval, analytics, mobile layouts and cache isolation. Provider success/failure contract responses are served by a local HTTP simulation; live model accuracy and provider retention settings remain operational checks after opting in.

The PUT signature binds the exact tenant staging key, Content-Type, Content-Length and SHA-256 metadata. Browsers send raw Blobs with no cookies; independent size/MIME signature/SHA-256 verification remains mandatory before a checked buffer is written with `If-None-Match: *` to a fresh server-only verified key. Optional AWS SDK checksum/trailer modes are disabled for R2 compatibility. Presigned URLs are sensitive bearer capabilities valid for at most ten minutes, reusable only for their staging object. R2 privacy, bucket-scoped credentials and origin-specific PUT CORS must be configured by the operator; CORS alone is not authorization. See [R2_SETUP.md](R2_SETUP.md).

## Operational boundaries

Email verification/reset, MFA, antivirus scanning, local-data encryption and general role management are outside the accepted scope. Magic-byte/checksum validation is not malware scanning or proof that a media file decodes completely. Original AI output and audit history are sensitive tenant records; restrict service/backups access and define an organization retention policy before production data intake. There is no application deletion/retention scheduler.

Self-service registration remains public. The burst guard bounds work per peer/process; a broader public launch may need ingress abuse protection based on observed traffic. Restore or credential incidents should revoke sessions, rotate affected database/storage/provider identities, retain audit evidence, and verify another tenant cannot access the restored workspace. Backups do not recover work still only on an offline device.

Read [DEPLOYMENT.md](DEPLOYMENT.md) and [BACKUP_RESTORE.md](BACKUP_RESTORE.md) before operating a production environment. The Render gate applies before creation, linking, configuration, validation through an account, or deployment—not only the final deploy command.

## Cloudinary evidence adapter

Cloudinary uses authenticated raw assets and a bounded same-origin session upload route. The binary exception to JSON-only requests is restricted to PUT on valid evidence/generation UUID paths when Cloudinary is selected; the Origin guard still applies. Assignment, tenant, creator, editable state and active generation are checked before receiving bytes and rechecked under locks before provider writes. Size, MIME signature and SHA-256 are verified before upload and on every private server read. Verified promotion uses the checked buffer and overwrite-disabled UUID IDs. Downloads never disclose provider URLs; removal retains version checks and durable cleanup. Admin API enumeration and deletion are confined to the dedicated deployment namespace. Local simulations exercise authorization/integrity; verify actual authenticated raw access denial, provider limits and recovery before release.

## Vercel frontend / Render API

Vercel serves the static shell and uses a native same-origin API rewrite to the existing Render service; no additional backend or frontend secrets are introduced. Host-only session cookies retain HttpOnly/Secure/Lax. Render CORS/preflight and CSRF permit only exact approved origins, including the legacy shell during staged acceptance. Cloudinary descriptors use the validated requesting origin, and all file authorization/integrity checks remain in Render. Vercel applies shell security headers and explicit no-store/no-CDN-cache policies to API rewrites. The service worker continues to bypass API/private responses; old-origin drafts stay isolated. Live login/evidence/offline acceptance and the final retirement of Render frontend serving are pending because Render CLI login expired and dashboard browser automation stopped.
